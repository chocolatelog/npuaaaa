执行摘要
    
你这道题与近两年研究前沿的重合度其实很高。赛题不是普通的“多核任务分配”，而是一个典型的 Graph Partition + Scheduling + Memory Planning + Bandwidth Contention + Pipeline Overlap 联合优化问题：场景 A 强调切图与 DDR 通信，场景 B 新增同核 L1/UB 驻留与缓存压力，场景 C 又加入 1 MB、250 bytes/cycle 的共享只读 L2；同时所有核共享 60 bytes/cycle DDR，核内有 Cube、Vector、MTE2、MTE3 多条可并行 Pipe。题目给出的商业芯片具体型号未指定，但硬件抽象与华为 Ascend/Da Vinci AI Core 非常接近；正式评价仍应以题目自带模拟器为唯一准绳。fileciteturn0file0
    
调研后的核心判断是：不要把主线押在“纯 GNN + 纯 RL”上。 2024–2026 年与这道题最贴近、而且最有工程说服力的工作，反而越来越强调：
    
DAG结构+显式Memory Cost+硬件Cost Model+约束搜索+Compute/DMA Overlap
    
2026 年针对 Da Vinci 风格 NPU 的 DAN-Scheduler / LATTICE 已经非常直接地证明：操作顺序、张量生命周期、L1/UB 峰值、spill/reload、DDR 流量以及 Cube/Vector/MTE 流水不能分开优化。其三阶段方法把峰值片上内存、额外 DDR 流量、spill 和 modeled makespan 相对最佳外部基线分别降低约 18.3%、20.4%、14.1% 和 16.3%。这与你们场景 B 几乎是“一一对应”的研究问题。需要注意，该工作目前是 2026 年 arXiv 预印本，而非我会优先当作已正式顶会录用结果来引用。[1]
    
第二个非常值得重视的结论来自 2026 年 ACM TACO 的 NPUMeter：它针对 Ascend 910B 建立 Cube、Vector、MTE、memory hierarchy 的白盒解析性能模型，平均时延预测误差低于 5%，将设计空间搜索由小时级降至分钟级，并获得最高 1.46× 的算子性能提升。它非常适合你们题目的“5–10 分钟求一个用例”限制，说明准确但便宜的 surrogate/cost model 很可能比直接用官方 evaluator 暴力搜索更重要。[2]
    
场景 C 最值得参考的是 CaMDN。它虽然研究的是多租户集成 NPU，而不是你们严格意义上的只读 FIFO L2，但实验明确说明共享 Cache 冲突与数据复用顺序会显著影响 NPU 性能；其 cache-aware mapping + dynamic allocation 平均减少 33.4% memory access，并实现平均 1.88×、最高 2.56× model speedup。对你们而言可借鉴的不是其硬件改造，而是“根据共享输入、reuse distance 和可用 cache capacity 做放置与调度”这一思想。[3]
    
GNN/RL 方向近两年确实活跃，但最贴近你们题目的结果主要来自通用 DAG / heterogeneous workflow scheduling，而不是多核 NPU 编译器。WeCAN、GrapheonRL 和 RELMAS 分别证明了 attention/GNN 表示、RL 策略以及 bandwidth-aware state 可以帮助调度，但将它们直接移植到本题仍有较大的训练、泛化和合法性风险。[4]
    
因此，我给你们的最终技术优先级是：
    
第一优先：Hardware-aware 图划分 + Critical-path/List Scheduling + 局部搜索。第二优先：Memory-pressure-aware 生命周期优化 + Cache-aware fusion。第三优先：共享 L2 reuse-distance-aware 调度。第四优先：训练一个快速 ΔMakespan Cost Model 加速搜索。第五优先：GNN/RL 只作为候选生成器或搜索引导器，而不是最终裁判。
    
从论文创新表达上，可以概括成：
    
“面向多核 NPU 的分层约束感知联合调度：联合优化计算图划分、缓存生命周期、共享带宽和异构流水并行。”
    
这比单纯写成“GNN 调度算法”更贴赛题、更像当前真正的 NPU compiler 研究。

工业编译器资源与可复用模块
    
    
华为 Ascend / CANN：与你们模拟器最接近
    
华为官方 Ascend C 文档将 AI Core 描述为 Cube、Vector、Scalar 加 MTE DMA 和多级 Local Memory 的结构；MTE2 负责 GM 向片上存储搬入，MTE3 等负责搬出，不同指令队列可异步执行，并依赖显式同步信号保证跨队列正确性。这与你们题中 PIPE_M、PIPE_V、PIPE_MTE2、PIPE_MTE3 的抽象几乎可以直接对照。[17]
    
官方文档：Ascend C 基础硬件架构Ascend C 硬件架构抽象
    
特别建议认真看 Ascend 官方的 DoubleBuffer 文档：CopyIn/Compute/CopyOut 分别位于 MTE2、Vector/Cube、MTE3 队列，因此数据搬运可以与计算重叠；官方用一个简单例子说明，如果三阶段均耗时 t 且完全串行，Vector 有效利用率只有约 1/3。这正是你们应该纳入 subgraph score 的“pipeline overlap potential”。[18]
    
Ascend C DoubleBuffer 官方文档
    
更有价值的是官方 GroupedMatmul 性能调优案例：调整 AIC/AIV 比例后耗时由 218.1 μs 降至 154.2 μs；增加 workspace 以减少 Cube/Vector 相互等待进一步降至 131.8 μs；Vector double buffer 后降至 128.1 μs。这个案例说明“多给缓存空间”和“提高并行度”之间并不是简单单调关系，而是 workspace/caching 与 pipeline stall 的联合问题。[19]

OpenXLA：最值得抄的是 Cost Model
    
OpenXLA 的 Latency Hiding Scheduler 直接对 HLO DAG 做 wall-time-aware scheduling，其 cost model 不是一个单一黑盒模型，而是把实测 performance table 与 analytical model 混合：GEMM、collective 等可使用 profiling table，对网络和 fusion 则使用解析模型。这种“粗模型筛大量方案 + 精确 evaluator 验少量方案”的结构特别适合你们 5–10 分钟的时间限制。[20]
    
OpenXLA LHS Cost Model
    
XLA 还在 schedule 之后进行 buffer assignment，利用整个计算图的信息来控制 intermediate memory；这与场景 B 中“同样合法的拓扑序会造成不同 tensor lifetime 和不同 L1/UB 峰值”完全同方向。[21]
    
OpenXLA GPU Architecture / Buffer Assignment
    
    
    
Apache TVM：最值得抄的是 Fusion + 搜索框架
    
TVM Relax 的 FuseOps / FuseTIR 会在 dataflow graph 上进行自动 operator fusion，并通过 post-dominator 等图结构分析处理分支；fusion 的核心收益包括去掉中间 buffer 的 global-memory 写回/再读取。它与本题“合并强通信子图减少 DDR，但过度融合又损失并行性和加大 cache pressure”本质相同。[22]
    
TVM Operator Fusion
    
TVM MetaSchedule 则代表另一条非常值得借鉴的工业路线：用便宜的 cost model 对巨大调度空间排序，然后只测量部分候选；框架本身提供 XGBoost、MLP 等 cost model，以及有限 trial budget。[23]

一个非常关键的设计原则是：
    
官方 Evaluator 是 Judge，不应该是每一步 Search 的 Cost Function
    
更实际的是：
    
104∼106 个候选→廉价 surrogate→Top-K→官方 evaluator
    
这与 NPUMeter 的解析模型 + DSE、XLA 的 profiling/analytical hybrid model，以及 TVM MetaSchedule 的 cost-model-guided search 都是一致的工程思想。[25]

稳妥路线：通信感知图划分 + Critical-Path List Scheduling + 局部搜索
    
这是我最建议你们先做出来的主干。
    
步骤一：图预处理。
    
把 Op-Tensor 二部图转成 Op DAG。对每个 Op 建立：
    
xv=[cycles, pipe, depth, bottomLevel, fanout,inputBytes, outputBytes]
    
对每条 Op→Op 逻辑边建立：
    
eij=[tensorSize, reuseCount, sharedInputFlag]
    
步骤二：生成初始子图。
    
定义 merge gain：
    
Gmerge(i,j)=α⋅SavedDDR(i,j)+β⋅SavedLaunchSync(i,j)−γ⋅ParallelLoss(i,j)−η⋅MemoryRisk(i,j)
    
场景 A 让 SavedDDR 权重大；场景 B 增大 MemoryRisk 权重。
    
步骤三：Core assignment。
    
用 critical-path/list scheduling：ready subgraph 中优先调 bottom-level 高的任务，对每个核心估计 earliest finish time：
    
EFT(s,c)=EST(s,c)+T(s,c)
    
这里的 T 至少应考虑当前核心负载、前驱通信、DDR congestion proxy，而不是只看 compute cycles。
    
步骤四：局部搜索。
    
只做四类动作：
    
Merge, Split, Move, Swap
    
每轮先用 surrogate 筛选，Top-K 再跑官方 evaluator。
    
步骤五：多起点。
    
至少生成：
    
critical-path-biased；
    
communication-biased；
    
load-balance-biased；
    
三个初始解，再统一 local search。

进阶路线：Memory-Pressure-Aware 场景 B
    
这条路线是最有可能成为你们论文核心创新的。
    
核心思想来自 LATTICE，但要改造成“多核切图版”：
    
Partition→Core Assignment→Lifetime-aware Ordering→Pipeline Refinement
    
LATTICE 的关键观察非常适用于本题：即使两个执行顺序都是合法拓扑序，不同顺序也会造成完全不同的张量 lifetime overlap、L1/UB 峰值和 spill 流量；其测试中不同合法顺序甚至导致很大的 memory-peak 与额外 DDR 流量差异。[1]
    
因此不能只判断：
    
“A、B 在同一核心，所以不需要 DDR，合并肯定好。”
    
而应判断：
    
NetBenefit=SavedCrossCoreDDR+SavedBoundaryCopy−PredictedSpill−ParallelismLoss
    
进一步建立 tensor lifetime：
    
Life(t)=[produce(t),lastUse(t)]
    
并估计：
    
PeakL1=maxkt:k∈Life(t),pos(t)=L1​size(t)
    
PeakUB=maxkt:k∈Life(t),pos(t)=UB​size(t)
    
当预测 peak 接近题目 L1=512 KiB 或 UB=128 KiB 时，显著增加 fusion penalty。题目本身明确规定这些容量，并会在不足时自动插入换出/换入。fileciteturn0file0

这里“B 一定快于 A”也不能作为数学保证，因为过长 tensor residence 可能增加 spill；这一点题目自己也明确提醒了。fileciteturn0file0
    
    
    
进阶路线：Reuse-Distance-Aware L2 Scheduling
    
问题 C 不应该只写成：
    
“有 L2，所以访问更快。”
    
真正的决策变量是：
    
通过切图、分核、执行顺序改变共享输入的访问时间关系，从而改变 FIFO Cache 是否仍保存该 tensor。
    
先构造 shared-input hypergraph：
    
Tensor X ├── Subgraph A / Core 0 ├── Subgraph B / Core 1 ├── Subgraph C / Core 3 └── Subgraph D / Core 4
    
定义一个简化 reuse score：
    
ReuseScore(t)=size(t)×(#consumers(t)−1)×Phit(t)
    
其中 Phit 通过你们自己实现的 1 MB FIFO 模拟器预测。
    
真正应优化的是：
    
BenefitL2≃HitBytesBL2−HitBytesBDDR,eff−DelayCost
    
因为题目 L2 是 250 bytes/cycle，而 DDR 总带宽只有 60 bytes/cycle，并且两者独立；因此共享输入在 L2 命中不只是减少 DDR bytes，还能缓解其他 core 的 DDR contention。fileciteturn0file0
    
但要特别注意：
    
Cache hit rate 不是主目标，Makespan 才是。
    
一个方案可以把相关消费者都挤到一起使 hit rate 从 50% 提到 80%，却因为破坏并行度让 Makespan 变差。CaMDN 同样说明 cache placement/scheduling 的价值来自最终 memory-access 与 latency 改善，而非“命中率越高越好”。[3]

场景 C 指标

≥1.08 有明显效果
较好的目标
1.12–1.20
全用例 byte hit rate
40–60% 可以作为初始工程目标
shared-input-heavy 子集
≥60–70% 值得冲击
L2 hit 提升但 Makespan 恶化的 case
必须单独分析，不能只报平均 hit
    
如果正式数据本身共享输入很少，那么 70% hit rate 根本不应作为强制目标，应先按“每个图可理论复用的 COPY_IN bytes”计算一个 oracle upper bound。
    
    
    
进阶路线：Hardware-Aware ΔCost Model
    
这是我认为性价比甚至高于 GNN的一条路线。
    
与其训练一个模型直接回答：
    
“这个完整调度方案需要多少 cycles？”
    
不如训练：
    
f(s,a)→ΔMakespan
    
其中动作 a 是：
    
merge 两个 subgraph；
    
split；
    
move 到另一 core；
    
swap order。
    
特征只需要：
    
[ΔcomputeBalance,ΔcutBytes,ΔcriticalPath,ΔL1Peak,ΔUBPeak,Δreuse,ΔDDRConcurrency]
    
第一阶段可直接用 XGBoost / LightGBM 类回归模型，甚至线性模型；没必要一开始上 GNN。
    
训练数据可以自动从官方 evaluator 生成：
    

    
建议评价 Cost Model 不只报 MSE，而报：
    
MAPE, SpearmanRank, TopKRecall
    
真正重要的是“能否把真正好的候选排进 Top-K”，而不是 cycle 预测绝对值是否极其精确。NPUMeter 的结果很好地说明，准确的硬件模型能够把设计空间搜索从小时级压到分钟级；OpenXLA 与 TVM 也都采用 cost model / measurement 辅助搜索。[25]

搜索空间太大，而且非法方案太多。

训练步骤建议：

最终建议与阅读顺序
    
从“做比赛、写论文、控制风险”三个角度综合，我建议你们的最终方案不要命名成简单的 GNN Scheduler，而可以设计成类似：
    
HAMPS：Hardware-Aware Multi-core NPU Partitioning and Scheduling
    
整个算法分四层：
    
Communication-Aware Partition
    
⇓
    
Memory-Pressure-Aware Core Mapping
    
⇓
    
Bandwidth / Cache-Aware Ordering
    
⇓
    
Pipeline-Aware Local Refinement
    
然后学习模块是可插拔的：
    
Learned Cost Model / GNN Search Guide
    
而不是让神经网络取代整个系统。
    
三个问题因此可以统一写成一个多目标约束优化：
    
minΠ,P,C,O Tmakespan+λ1DDDR+λ2Sspill+λ3Pcache+λ4Iimbalance
    
其中：
    
Π：图切分；
    
P：subgraph → core placement；
    
O：core 内顺序；
    
C：cache / data-residency 行为；
    
$D_{\rm DDR}$：额外 DDR 通信；
    
$S_{\rm spill}$：L1/UB overflow 的 spill 风险；
    
$P_{\rm cache}$：L2 miss / reuse-distance penalty；
    
$I_{\rm imbalance}$：多核和 Cube/Vector 负载不均。
    
最终真正由官方 evaluator 给出的：
    
Tmakespan
    
仍是主目标，其余项只是搜索 surrogate。这个区分非常重要。
    
实际阅读顺序，我建议如下：
    
第一篇：DAN-Scheduler / LATTICE。先建立“为什么 order、cache、spill、DMA 必须联合优化”的完整认识。这篇与你们题目 B 的结构相似度最高。 arXiv [1]
    
第二篇：NPUMeter。重点读 performance model，而不是算子优化细节。你们可以直接仿照其思路做“比赛 evaluator 的廉价代理模型”。 ACM [2]
    
第三篇：MAS-Attention。重点看 matrix/vector 两流怎么划分、tiling 怎样兼顾 I/O、为什么主动控制 cache overwrite 能避免 spill。 MLSys [5]
    
第四篇：HyperParallel-MoE。重点看 Ascend NPU 上的 event-driven static taskflow 和 AIC/AIV 并行，帮助你们设计场景 B 的同步/流水调度表述。 arXiv [6]
    
第五篇：CaMDN。专门为问题 C 服务，重点看 shared cache contention、cache-aware mapping、reuse。 arXiv [3]
    
第六篇：PipeThreader。用来完善“Task graph + heterogeneous execution unit + software pipeline”这一层。 OSDI 2025 [7]
    
之后才是 WeCAN → GrapheonRL → RELMAS。它们适合解决“我们还想再加一个 GNN/RL 创新点”的问题，而不是解决“基础调度到底怎么才能做好”的问题。[4]
    
综合最近两年的文献与工业实现，我认为这道题最值得做成的创新不是：
    
“我们使用强化学习替代传统算法。”
    
而是：
    
“我们提出一个面向多核 NPU 的分层硬件感知联合优化框架，以通信收益驱动计算图划分，以 tensor lifetime 驱动核内复用，以共享带宽与 L2 reuse distance 驱动跨核排序，并通过多 Pipe critical-path refinement 恢复计算—搬运并行；进一步利用学习型 cost model 加速 5–10 分钟预算内的组合搜索。”
    
这个表述同时能覆盖 A、B、C 三个问题，而且与 2024–2026 年真正有代表性的 NPU compiler / accelerator scheduling 研究趋势是对齐的。[27]
